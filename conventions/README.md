# Conventions

What every rendered build keeps, whatever its answers. A workspace (`workspace` yes) keeps the
rows marked so. Estate conformance (D4 in the house)
compares a repo against this list and against the blueprint tag its `.copier-answers.yml`
names.

| Convention | Rule |
|---|---|
| `CLAUDE.md` | Identity and routing only. Under 80 lines. Every rule carries its why where the why is not obvious. |
| Tickets | `.icm/intake/`: an epic is a folder with `breakdown.md` and one stub per unit of work. A one-off is a triage stub. The path is the identity. The folder is the status. The contract is `.icm/intake/CONTEXT.md`, rendered by the blueprint. A user story becomes one epic. The story stays in the client's Drive. The breakdown's `Criteria → stubs` table shows where each criterion went. |
| Pull requests | One ticket is one branch and one pull request. The body follows `.github/pull_request_template.md`: the two gates at the top, anchored by `<!-- gate:spec-approved -->` and `<!-- gate:ready-to-merge -->`, then the ticket path, what changes, the acceptance criteria and how to test. The pull request moves the stub into `_done/`. |
| Lanes | A one-off follows a lane: `.icm/lanes/<lane>/CONTEXT.md`, the blueprint's. The four lanes are `bug`, `tweak`, `chore` and `hotfix`. A lane says only what differs from the loop in `.icm/intake/CONTEXT.md`. The session writes the triage stub first, then follows the lane. Jamie invokes `hotfix`, never a hook or an alert. Each lane keeps `## Inputs`, `## Process` and `## Outputs`, under 60 lines. |
| Scripts | The scripts in `.icm/scripts/` are the blueprint's. `new-run.sh` starts a ticket. `--ready` opens the pull request ready, for the hotfix lane. `--dry-run` prints the branch and the body and creates nothing. `close-out.sh` finishes an epic. `merge.sh` merges one pull request after the Ready to merge tick. `release.sh` merges the release pull request on Jamie's word `release`. Each script does the mechanics of one step and decides nothing. Without the tick or the word, `merge.sh` and `release.sh` refuse. |
| UAT | A build that answered yes to `uat` carries `.icm/uat/CONTEXT.md`, the blueprint's. Every merge to `main` deploys the Vercel custom environment `uat` and builds a staged production deployment. The client tests the batch at the UAT address. `promote.sh approve --by` records the sign-off on the release pull request, on Jamie's word. On Jamie's word `release`, the session merges the release pull request with `release.sh`. That merge makes the tag and moves nothing. On Jamie's word `promote`, the session runs `promote.sh run --tag <tag>`. The script dispatches `promote.yml`: it migrates production, then promotes the staged build. The UAT database is apart from production's. With `neon`, UAT and production are two Neon projects. The base is the UAT project's default branch, and `preview-db.sh` cuts a preview's branch from it for a migration. A rollback is `rollback.sh`'s printed command, Jamie's to run. Without UAT the pull request preview is the UAT and production follows `main`. |
| Gates | Human checkboxes. A session reads them and never ticks them. Jamie ticks on GitHub or from the desk. A `low` stub and a triage stub carry no Spec approved gate. A missing anchor means not required. After the Ready to merge tick, the session merges with `merge.sh`. |
| Commits | Conventional Commits. The type comes from the table in `.icm/intake/CONTEXT.md` § Commit types: `feat:` for a feature stub, `fix:` for the bug and hotfix lanes, `fix:` or `style:` for a tweak, `chore:`, `refactor:`, `build:` or `ci:` for a chore, `docs:` for a docs change. The squash merge makes the pull request title the commit on `main`. With `release` yes, the release is Jamie's word `release`, and the session runs `release.sh`. With no, production follows `main` and the merge is the release. |
| Writing | Technical text in Simplified Technical English: stubs, breakdowns, pull request bodies, commit messages, hook text. Questions for Jamie are numbered and carry a default answer. Client-facing text in the client's language. |
| CI | `ci.yml` calls the reusable workflows in `legible-consulting/.github`. Nothing is copied in. Never run build, lint, typecheck, test, format or dev locally. |
| Claude assets | `.claude/settings.json`, the six hooks in `.claude/hooks/` and the three skills in `.claude/skills/` are the blueprint's, byte for byte, so cloud sessions are guarded too. The hooks are the three guards (`block-local-checks.sh`, `confirm-git-writes.sh`, `guard-plaintext-secrets.sh`), the router `route-request.sh` and its test `route-request.test.sh`, and the board `session-start.sh`. The skills are `pr-conventions`, `ticket-craft` and `asd-ste100`. A workspace keeps `settings.json` and the three guards, and has no router, no board and no skill. |
| Workspace | A workspace keeps: `CLAUDE.md` as the map, under 80 lines, one routing row per stage. One folder per stage, numbered, each with a `CONTEXT.md` that has `## Inputs`, `## Process` and `## Outputs`. At least one gate that names the role of the person who ticks it. `ci.yml` calls `check-client` with `workspace: true`. No `.icm/`, no pull request template. It passes `workshop-kit/walk-test.md`. |
| Database | A build that answered `neon` to `database` carries `.icm/database/CONTEXT.md`, the blueprint's. The base is UAT's database with UAT, production's without. Every preview reads the base. A pull request that changes `<migrations_path>/**` gets the Neon branch `preview/<git branch>`, cut from the base by `preview-db.yml`, deleted by `neon-cleanup.yml`. A deployment migrates at build only where `MIGRATE_AT_BUILD` is `1`. Any other answer renders no database file. |
| Secrets | Never in git. A workspace keeps this row. Names only, in an `.env.example`. Values in GitHub or Vercel settings. A UAT or Neon build's scripts and workflows read `VERCEL_TOKEN`, `NEON_API_KEY` and `DATABASE_URL` as secrets, `VERCEL_TEAM`, `VERCEL_PROJECT` and `NEON_PROJECT_ID` as variables. |
